## 1. 停止失效（最高优先）

### 结论与根因

“点击停止 → 一直正在停止 → 红色操作超时”有两个叠加成因：

1. **事件循环被检索阻塞**：旧实现每次 `searchNotes` 全库重扫，交接文档记录的 400 篇合成库暖查询耗时 14.5 秒且最大事件循环滞后 14.4 秒，等于整个查询期间读不到 stdin 的停止命令。前端 30 秒 ack 超时因此触发“操作超时，请检查 Agent 连接”。本轮检索修复后同环境最大滞后 29~58ms（400 篇）/105~148ms（1200 篇）。
2. **停止链路本身缺少终态保证**（与阻塞无关，单独也可复现）：
   - 没有当前任务时按停止，只回 `ack` 与 `stopping`，没有任何终态，界面永久停在“正在停止”。
   - `promptId` 过期时只回 `ack{stale:true}`，前端不处理 `stale`，`stopping` 标志永久为真，停止按钮永久禁用。
   - 旧轮的 `done`/`session_sync` 不带轮次身份，迟到的结束事件会关闭新一轮界面。

### 修复

- `bridge.mjs`：`abort` 先 `ack`（带 `stale`）再 `stopping`（带 `turnId`）；无当前任务时立即 `session_sync{busy:false}`；`started`/`done`/`session_sync`/`stopping` 全部携带 `turnId`，只有仍持有生命周期的轮次才能发布终态并清 `busy`。
- `turn-watchdog.mjs`（新增）：取消后 15 秒升级提示、30 秒本地强制结束；强制结束时 `dispose` 旧会话、清 `busy`、发 `turn_forced_end`，并明确告知“服务端可能仍在处理”，随后重建会话（不假装上游已停）。时限可用 `SUMMON_ABORT_ESCALATE_MS`/`SUMMON_ABORT_FORCE_MS` 覆盖（仅供测试/运维）。
- `app.js`：处理 `stale` ack；按 `turnId` 过滤迟到终态；`abort` 超时不再留死状态（可再次点击停止）；`abort` 命令超时从 30 秒收紧到 15 秒。

### 证据

- 新增 `desktop/agent/stop-lifecycle.integration.test.mjs`（真实 bridge 子进程 + 本地停滞 HTTP 端点）4 项：无任务停止回到空闲、已完成轮次的 stale 停止仍同步状态、停滞上游停止后 done/`session_sync` 终态并可继续下一轮、终态按轮次有序不污染下一轮。**在 `b20e27d` 之前 0/4 通过，之后 4/4 通过。**
- 新增 `desktop/agent/turn-watchdog.test.mjs` 4 项（升级一次、结算后解除、新轮次替换旧轮次、无轮次 id 不武装）。
- 原生打包应用验收新增用例：正文停滞请求点停止后 **73ms** 内回到空闲、无错误残留、下一条消息正常完成（`dist/acceptance/report.json`）。

### 未覆盖

- 真实 DeepSeek 服务端“已收到请求但拒绝取消”的行为无法在无付费授权下复验；本地强制结束路径由单测覆盖，未在真实官方接口上触发。

## 2. 笔记库总览超时

### 修复

- 检查点升级为 v4：按批次下标保存结果（`results`），失败批次单独记录（`failed`），**单个批次超时/长度失败不再中止整轮**，其余批次继续，重试只重新请求缺失批次。仍能读取旧 v3 的稠密摘要数组，避免重复付费重跑。
- 压缩阶段失败降级：把已有批次摘要截断到 14000 字继续汇总，并在总览文件内标注“最终汇总只读取了部分摘要”；不再整轮失败。
- 失败批次写入总览文件“未纳入”段（批次数），状态事件带 `done`/`batches`/`failed` 计数，用户能看到真实进度。
- 后台请求分离 idle 与 total 上限：总览单次请求 total 5 分钟、**idle 2 分钟**（`idleTimeoutMs`），静默流不再以“无限等待”占住共享端点槽位 5 分钟。

### 证据

- `desktop/agent/vault-reliability.test.mjs` 12 项通过（原 10 项 + 新增 2 项）：三批中单批超时后仍生成总览并标注 1 批未完成、重试只请求失败批次和最终汇总（断言第二次请求的输入正是失败批次）；压缩失败仍产出总览并标注未完整覆盖。
- 断言 `requestTimeoutMs=300000`、`idleTimeoutMs=120000` 实际传入请求层。

### 未覆盖与风险

- **未使用真实官方 DeepSeek 接口验证 medium 总览**（无付费授权）。批次预算（off 1800，medium +8192，受模型 maxTokens 上限约束）仍是候选策略，不是官方超时根因结论。
- 大库总览的批次数与总耗时取决于真实笔记库规模，本轮只验证了失败恢复与不丢进度，未给出真实库的完成时间承诺。

## 3. 主对话检索性能

### 根因（实测定位）

用临时插桩脚本定位到暖查询的同步阻塞构成（1200 篇合成库、31,200 个段落）：

| 环节 | 修复前 | 说明 |
|---|---|---|
| 一次性读出全库分块元数据 | ~312ms 单次同步 | 每次检索都读 |
| `retain` 全表扫描 | ~128ms 单次同步 | 即使没有删除 |
| 每次检索重开数据库并重跑一致性迁移检查 | ~40ms/次 | 每次检索 |
| 扩词查询各自全库重扫 | ×4 | 一次检索最多 4 次全扫 |
| FTS 查询 | ~114ms | 保留（见下） |

### 修复

- `searchMany`：一次检索规划里的原问题 + 最多 3 个扩词共用**一次**扫描与索引更新，N 次 FTS 复用同一索引。
- 逐文件按 `id` 前缀做索引区间查询（`(area,scope,id)` 上的范围扫描），不再一次性把全库分块元数据读进 JS。
- 索引常驻会话，不再每次检索重开并重跑迁移/一致性检查（改为每次启动一次 + 行数校验自愈）。
- `retainPaged`：按主键分页扫描并逐页让出事件循环，避免单次长事务。
- 元数据迁移放进**单一事务**，迁移中用行数比对自愈中断/重复/孤儿文档（修复交接文档点名的“建表与回填没有同一原子事务”风险）。
- 逐文件让出事件循环改为每 16 个文件一次（文件内取消检查仍然逐文件）。

### 同环境测量（合成库，`desktop/tools/vault-performance.mjs`，原始输出见 `docs/perf-0.2.2-round2/`）

| 规模 | 冷查询 | 暖查询 | 重复查询 | 最大事件循环滞后 |
|---|---|---|---|---|
| 400 篇（旧版基线） | 180692ms | 14527ms | 14461ms | 1053 / 14477 / 14402ms |
| 400 篇（本轮） | 1304~1809ms | 167~238ms | 151~238ms | 29~58ms |
| 1200 篇（本轮） | 4491~5413ms | 468~687ms | 639~687ms | 105~148ms |

剩余最大同步块是 FTS5 的 bm25 排序（约 105~150ms/次，1200 篇），可接受；未引入 worker 线程。测试用例：`local-search.test.mjs` 新增“一次检索多个查询只扫描一次”“中断/重复元数据自愈”“迁移不产生重复文档”；`note-retrieval.test.mjs` 新增扩词合并、精确命中不扩词、取消后不再扫描。

### 向量/RAG 适用性（按交接要求只做分析，不引入）

现状是本地 SQLite FTS5（中文二元切分）+ 可选模型扩词，没有 embedding。向量或混合检索能改善**同义/语义召回**，但不会改变本轮的四类根因：事件循环同步阻塞、HTTP 超时与取消、模型串行额度排队、后台任务与主对话抢占。因此本轮先用现有路径把阻塞和终态修好；是否加向量库需要单独评估 embedding 成本、离线可用性与笔记隐私，不属于本轮范围。

## 5. 追加：总览批次并行（用户要求，`2bb4979`）

### 结论

之前**不能**并行：共用模型额度确实支持并行槽位，但总览的批次循环是严格串行的，永远只发一个请求。现在批次改为动态工作池，并发数取“所选总览模型所在提供商”的并行设置（`parallelRequests` + `maxConcurrentRequests`，1~8）；未开启并行的提供商保持严格串行，行为与之前一致。

- 并发下检查点改为唯一临时文件 + 串行写入（避免多个 worker 争用同一路径），单批失败仍只补该批。
- 进度事件带 `concurrency`；总览文件在并发 >1 时记录“批次理解并发：N”；设置页状态行显示“并发 N”，说明文案也已更新。

### 模拟端到端证据（真实 bridge 子进程 + 本地模拟端点）

| 场景 | 请求数 | 并发峰值 | 结果 |
|---|---|---|---|
| 提供商未开启并行 | 4（三批 + 汇总） | **1** | 串行完成，总览不写并发标注 |
| 提供商开启并行（2） | 4 | **2** | 两个批次同时进行，全部完成 |

### 真实 DeepSeek 实测（用户授权：隔离 profile + 合成笔记库）

配置：`https://api.deepseek.com`，模型 `deepseek-flash`，思考 `off`，并发 2，6 篇合成笔记 → 2 批。**未发送任何真实笔记**，配置副本测试后删除。

| 观察点 | 实测 |
|---|---|
| 两个批次发出时刻 | 同一次事件循环（+208ms 同时出现“第 1/2 批”“第 2/2 批”） |
| 连接与首包 | 两批均在同一时刻进入 headers/first_body（+823ms） |
| 批次耗时 | 批次 2：11→3159ms；批次 1：0→4056ms（重叠） |
| 最终汇总 | 4072→9181ms |
| 整轮 | 9.5 秒完成，0 失败，`concurrency: 2` |
| 请求诊断峰值 | 2 |
| 总览文件 | 含“批次理解并发：2（来自提供商的并行请求设置）” |

真实请求共 3 次（2 批摘要 + 1 次汇总），每次 `max_tokens=1800`。用户实际配置为 `maxConcurrentRequests: 5`，本轮按已确认范围用 2 验证；并发数完全由该设置决定（单测覆盖 1/3 两档，端到端覆盖 1/2 两档）。

## 8. 剩余计划

1. 用户在真实笔记库与官方 DeepSeek 上复验：停止（正文停滞/思考中/排队）、medium 总览（可用本轮的并行并发数缩短总时长）、检索首字延迟。需要用户明确授权付费调用与真实笔记访问。
2. 若真实总览仍在某批次超时，按本轮新增的 `done/batches/failed` 计数与 `request-diagnostics.jsonl` 阶段日志定位到具体批次与阶段，再决定是否调整批次大小、思考预算或并发数。
3. 并行数是“所选总览模型所在提供商”的设置（当前 DeepSeek 为 5）：批次多于并发时会排队；调高并发会同时占用更多服务额度，可按实际限流调整 `maxConcurrentRequests`。
4. 大库（>2000 篇）FTS 排序仍是单次约 150ms 同步块；如需更低延迟，下一步是把索引与检索移入 worker 线程（本轮未做，避免在 Windows 上引入 SQLite 多进程写入风险）。
5. 推送源码、按用户指示更新同一个 Release Draft 附件（保持 Draft）。
